# Implementation Plan: BCM User Resource (bcm_cmuser_user)

**Branch**: `068-cmuser-user-resource` | **Date**: 2025-11-26 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/068-cmuser-user-resource/spec.md`

**Note**: This plan follows the project's TDD methodology (RED-GREEN-REFACTOR) as documented in CLAUDE.md and AGENTS.md.

## Summary

Implement a Terraform resource `bcm_cmuser_user` for managing BCM Unix user accounts via the CMUser JSON-RPC API. The resource enables full CRUD lifecycle management (Create, Read, Update, Delete) plus Import functionality for DGX BasePOD automation workflows that require user creation before Kubernetes cluster user setup. Implementation follows the existing provider patterns (CMPartSoftwareImageResource, CMDeviceCategoryResource) with TDD approach using modern terraform-plugin-testing patterns (statecheck, plancheck).

## Phase 0: Research & Discovery

### Research Tasks

Based on Technical Context analysis, the following unknowns require resolution:

#### R-001: Verify CMUser API Methods for Resources

**Objective**: Confirm existence and signatures of `addUser`, `updateUser`, `removeUser`, `getUser`, `validateUser` methods.

**Research Approach**:
1. Test API methods via BCMClient from test helper
2. Verify response formats match spec.md contract
3. Document any deviations from assumed behavior

**Expected Methods**:
| Method | Service | Arguments | Expected Response |
|--------|---------|-----------|-------------------|
| getUser | cmuser | username (string) | User entity object or null |
| addUser | cmuser | entity (object), force (bool) | UUID string or object |
| updateUser | cmuser | entity (object), force (bool) | Success/entity object |
| removeUser | cmuser | username (string) | Success boolean |
| validateUser | cmuser | entity (object), isCreate (bool) | Validation array |

#### R-002: Verify User Entity Structure for Create/Update

**Objective**: Confirm BCM entity structure for user creation and update operations.

**Research Approach**:
1. Examine existing user via `getUser` to understand full entity structure
2. Test minimal `addUser` call with required fields only
3. Document required vs optional fields for create operations

**Expected Entity Structure**:
```json
{
  "baseType": "User",
  "childType": "",
  "modified": true,
  "to_be_removed": false,
  "revision": "",
  "uuid": "generated-or-empty",
  "name": "username",
  "password": "password-value",
  "ID": "1001",
  "groupID": "1001",
  "homeDirectory": "/home/username",
  "loginShell": "/bin/bash",
  "commonName": "Display Name",
  "surname": "",
  "email": "",
  "notes": "",
  "authorizedSshKeys": "",
  "shadowMax": 99999,
  "shadowMin": 0,
  "shadowWarning": 7,
  "shadowInactive": 0
}
```

#### R-003: Group Membership Handling

**Objective**: Determine how group memberships are managed for users.

**Research Approach**:
1. Query existing user with group memberships
2. Identify if groups are part of user entity or separate API call
3. Document group reference format (name vs UUID)

**Possible Patterns**:
- Groups as array in user entity (`groups: ["wheel", "docker"]`)
- Separate API call (`cmuser.addUserToGroup(username, group)`)
- Group IDs vs group names

#### R-004: UID/GID Auto-Assignment Behavior

**Objective**: Understand BCM behavior when UID/GID not specified.

**Research Approach**:
1. Create test user without specifying UID/GID
2. Verify BCM auto-assigns next available values
3. Document constraints on manual UID/GID assignment

## Implementation Patterns

### Resource Scaffold Pattern

Following `resource_cmpart_softwareimage.go`:

```go
// Ensure provider defined types fully satisfy framework interfaces.
var (
    _ resource.Resource                = &CMUserUserResource{}
    _ resource.ResourceWithImportState = &CMUserUserResource{}
)

type CMUserUserResource struct {
    client *BCMClient
}

type CMUserUserResourceModel struct {
    ID                types.String `tfsdk:"id"`
    UUID              types.String `tfsdk:"uuid"`
    Username          types.String `tfsdk:"username"`
    Password          types.String `tfsdk:"password"` // Sensitive
    // ... additional fields
}
```

### Password Handling Pattern

Password is write-only - BCM API returns empty string:

```go
// In Create/Update:
if !plan.Password.IsNull() {
    entity["password"] = plan.Password.ValueString()
}

// In Read:
// DO NOT set model.Password from API response (always empty)
// Preserve password from prior state
model.Password = state.Password
```

### Pre-flight Validation Pattern

Following CMPartSoftwareImageResource:

```go
// Build entity first
entity := r.buildAPIEntity(&plan, "")

// Validate before create
validationErrors, err := r.client.ValidateEntity(ctx, "cmuser", "validateUser", entity, true)
if err != nil {
    resp.Diagnostics.AddError("Validation API Error", err.Error())
    return
}

// Process validation results (ERROR vs WARNING)
for _, valErr := range validationErrors {
    if valErr.IsError() {
        resp.Diagnostics.AddError(fmt.Sprintf("Validation Error: %s", valErr.Field), valErr.Message)
        hasErrors = true
    }
}
```

### Import Pattern

Using username as import identifier:

```go
func (r *CMUserUserResource) ImportState(ctx context.Context, req resource.ImportStateRequest, resp *resource.ImportStateResponse) {
    // req.ID contains the username passed to `terraform import`
    // Set username attribute, then Read() will populate full state
    resp.Diagnostics.Append(resp.State.SetAttribute(ctx, path.Root("username"), req.ID)...)
}
```

### Drift Detection Test Pattern

Following test_helpers.go documentation:

```go
Steps: []resource.TestStep{
    // Step 1: Create user
    {
        Config: testAccCMUserUserConfig(username, "/bin/bash"),
        Check: resource.TestCheckResourceAttr("bcm_cmuser_user.test", "shell", "/bin/bash"),
    },
    // Step 2: Modify externally, detect drift
    {
        PreConfig: func() {
            client := createTestBCMClient(t)
            ctx := context.Background()

            // Get user data
            body, _ := client.CallJSONRPC(ctx, "cmuser", "getUser", username)
            var userData map[string]interface{}
            json.Unmarshal(body, &userData)

            // Modify shell externally (snake_case -> camelCase: shell -> loginShell)
            userData["loginShell"] = "/bin/sh"
            userData["modified"] = true

            // Update via API
            client.CallJSONRPC(ctx, "cmuser", "updateUser", userData, false)
            time.Sleep(2 * time.Second) // Eventual consistency
        },
        Config: testAccCMUserUserConfig(username, "/bin/bash"),
        ConfigPlanChecks: resource.ConfigPlanChecks{
            PreApply: []plancheck.PlanCheck{
                plancheck.ExpectNonEmptyPlan(), // Drift detected!
            },
        },
    },
    // Step 3: Terraform restores desired state
    {
        Config: testAccCMUserUserConfig(username, "/bin/bash"),
        Check: resource.TestCheckResourceAttr("bcm_cmuser_user.test", "shell", "/bin/bash"),
    },
}
```
