### Valid XML Design

**Minimal Valid XML for Testing**:

```xml
<?xml version="1.0" encoding="UTF-8"?>

<diskSetup>
  <device>
    <blockdev>/dev/sda</blockdev>
    <partition id="a0" partitiontype="esp">
      <size>100M</size>
      <type>linux</type>
      <filesystem>fat</filesystem>
      <mountPoint>/boot/efi</mountPoint>
      <mountOptions>defaults,noatime</mountOptions>
    </partition>
    <partition id="a1">
      <size>max</size>
      <type>linux</type>
      <filesystem>xfs</filesystem>
      <mountPoint>/</mountPoint>
      <mountOptions>defaults,noatime</mountOptions>
    </partition>
  </device>
</diskSetup>
```

**Rationale**:
- Includes required XML declaration
- Uses correct root element `<diskSetup>` (capital S)
- Contains proper `<device>` element (not `<disk>`)
- Includes `<blockdev>` to specify device path
- Defines two partitions (ESP boot + root) with all required child elements
- Matches BCM's documented schema structure
- Simple enough for test readability while remaining valid

## Risk Mitigation

**Risk**: BCM may have additional undocumented XML requirements beyond the visible structure

**Mitigation**: Use the exact XML structure from BCM's documented default category, which is known to work. Start with minimal subset and expand if validation fails.

**Risk**: XML string formatting may cause issues (whitespace, newlines)

**Mitigation**: Use Go's backtick multi-line string literals to preserve exact formatting. BCM has accepted similar formatted XML in other tests.

**Risk**: Test may still fail due to environment-specific issues

**Mitigation**: Test cleanup includes `testAccCMDeviceCategoryPreCheck()` to remove leftover resources. Use unique test names with timestamp to avoid conflicts.
